RSMC - WHAT EACH VERSION DID
============================

One or two lines per version, newest first. This file is the short form; CHANGELOG.md is
the detailed history and carries the reasoning. BOTH ARE MAINTAINED - every version bump
gets an entry in each.

The rule is adopted from rstweaks, where it was learned the hard way: versions 0.2.18
through 0.2.46 of that mod were never written down and the detail is unrecoverable.

0.10.0
------
  THE SHELL CONNECTS - Casing, Pattern Port and Controller. 0.9.3 shipped the tag but no Athena
  definitions, so nothing joined. Casing and Port get athena/*.json. The Controller cannot (a
  per-block definition replaces all twelve variants), so it uses Athena's geometry loader inside
  twelve per-facing models, loaded OPTIONALLY so there is still no dependency - one model per facing
  because Athena ignores blockstate rotation. Port and screen tiles are generated from the five
  casing tiles. Pattern Storage gets pattern_storage_top.png. assetCheck 79 -> 353, now proving
  every texture a model or definition names exists. Parsed by Athena headlessly; not seen in game.

0.9.3
-----
  THE SHELL GETS A TAG TOO, rsmbac:shell - Casing, Controller and Pattern Port - so the outside of
  the machine reads as one surface the way rsmbac:interior does for the inside. Athena's condition
  only ever tests the NEIGHBOUR, never the block asking, so tag membership and having a definition
  are separate things: the Controller is in the tag with NO definition of its own, which lets Casing
  and Port flow into it while it keeps its orientable model, its facing and its three screen states.
  Seven definitions when the art lands, not nine; the Frame is in neither tag on purpose.

0.9.2
-----
  THE INTERIOR GETS A BLOCK TAG, rsmbac:interior - the four CPU tiers plus Pattern Storage, the same
  set the shape code calls Role.INTERIOR. It exists for connected textures: Athena's connect_to
  takes a block tag, and the decision is that everything in the interior connects to everything
  else, so a 1x, a 64x and a Pattern Storage read as one surface rather than five bordered blocks.
  PLACEHOLDERS.md carries the tile naming and the exact JSON. The five Athena definitions are
  deliberately NOT shipped yet - they would render missing textures until the tiles are drawn.

0.9.1
-----
  EACH CPU TIER HAS ITS OWN TEXTURE SLOT. All four tier models pointed at one block/cpu, so a 1x
  and a 64x were the same pixels in a wall and the tier layout of a structure was unreadable.
  Split into cpu_1x/4x/16x/64x.png with each model on its own. The four files are still the same
  placeholder pixels - this opens the slots so the real per-tier art drops in without a model edit.

0.9.0
-----
  PROCESSING PATTERNS ARE NOW REFUSED AT EVERY DOOR, not merely unsupported. A processing pattern
  needs a PatternProviderExternalPatternSink to push its ingredients into; an autocrafter is one and
  the multiblock is not, and never calls setSink. RS does not treat that as an error --
  PatternProviderNetworkNode.accept opens with 'if (sink == null) return SKIPPED' -- so one sitting
  in a structure was still advertised as craftable, still planned into a task, and then STALLED
  FOREVER. /rsmbac import already refused to carry them in; that rule is now PatternPolicy, and it
  is enforced at the pattern screen, the Pattern Port and the push into the network node as well.
  The test is the pattern's LAYOUT type, not the item's: INTERNAL is a recipe RS runs, EXTERNAL is
  one it hands to a sink. Stonecutter and smithing patterns are internal and still work.
  THE BACKSTOP MATTERS MOST FOR EXISTING WORLDS. A pattern placed before this version is still in
  its slot on load. It is NOT deleted -- it stays where its owner left it and /rsmbac info goes on
  naming it -- but the Controller no longer hands it to the node, so it is inert instead of a task
  that hangs. Filtering there is free: the Pattern is resolved on that line either way.
  The client predicts the refusal from the stack's data component rather than by resolving it, so
  the render thread ClientPatternContainer exists to protect is not given back.
  3 new gametests (25 total), and the backstop one was checked by breaking the filter and watching
  it go red. The shared helper encodedPattern() was itself a PROCESSING pattern and had to stop
  being one -- a helper named 'a pattern a slot will take' cannot return the one kind no slot takes.

0.8.2
-----
  /rsmbac import IS NO LONGER OP-GATED. Reported as 'I can see /rsmbac info but no /rsmbac import'.
  The cause: a single-player world with cheats off puts the player at permission level 0, and
  Brigadier STRIPS failed nodes from the client command tree -- so the command was not refused, it
  was invisible, sitting next to info which has no requirement and worked fine. That world was a
  copy of someone else's survival save, which is exactly the case this command exists for.
  The gate is removed rather than lowered, because it protected nothing. Right-clicking the
  multiblock opens its pattern screen and lets ANY player take every pattern out by hand, with no
  permission check and never one; an autocrafter empties the same way through RS's Autocrafter
  Manager. The command offers no access that was not already there -- it only does it in one step
  and reports what it did. Gating it made the safe, reversible, reporting path harder than the
  tedious one.


0.8.1
-----
  THE IMPORT LEAVES PROCESSING PATTERNS ALONE. Caught before the command was ever run for real,
  as a side thought: "this pulls everything except processing patterns right?" It did not -- it
  pulled those too, and that would have been worse than useless.
  A processing pattern pushes its ingredients into a machine, so it needs a
  PatternProviderExternalPatternSink. An autocrafter IS one. The multiblock is NOT, and never calls
  setSink -- RS's PatternProviderNetworkNode.accept opens with "if (sink == null) return SKIPPED".
  So a processing pattern moved in here stays advertised as craftable, gets a task planned and
  dispatched, and stalls forever. The recipe worked before the import and silently does not after,
  and it reads as the multiblock being broken rather than the migration being wrong. It also
  contradicted the mod's own stated scope, which has said since 0.0.1 that you cannot parallelise a
  furnace by building a bigger cube.
  THE TEST IS THE LAYOUT TYPE, NOT THE ITEM'S. RS builds crafting, stonecutter AND smithing layouts
  with PatternLayout.internal and only processing with external -- verified in the bytecode of the
  four PatternResolver.Resolved*Pattern classes. INTERNAL means "RS runs this itself", which is
  exactly the set the multiblock accelerates, so all three of the first kind move and only
  processing stays. Filtering on the item's pattern type instead would have been a naive
  "crafting only" and silently stranded stonecutter and smithing recipes; that mistake now fails a
  gametest.
  Unresolvable patterns are left alone too -- one that cannot be read is not one to move somewhere
  it will be even less readable.
  The dry run reports the count before anything moves, so the number is visible either way.
  Verified by breaking it twice: a crafting-only filter strands the stonecutter pattern, and the
  test says so by name. 22 gametests.


0.8.0
-----
  /rsmbac import -- MOVING PATTERNS OUT OF AUTOCRAFTERS, WHICH NOTHING ELSE CAN DO.
  Reported from the migration attempt: "SFM can't pull from mega autocrafters, and if SFM can't I
  don't think any mod can." Correct, and verified in both jars. Refined Storage registers
  Capabilities.ItemHandler.BLOCK for its Disk Drive and Interface ONLY -- not the Autocrafter.
  Cable Tiers registers one for its Disk Interfaces and Interfaces, and gives its tiered
  autocrafters only the network-node capability. There is nothing for any hopper, pipe or SFM to
  pull from; patterns were always meant to move through the Autocrafter Manager screen by hand.
  So the move is made from inside. It is also the better tool: no transport mod in the middle to
  void a stack, no item entities, and it reports what it did.
  DUPLICATION IS THE SAFE FAILURE, DELETION IS NOT. Each pattern is written to the destination and
  READ BACK before it is removed from the source, so a failure between the two leaves it in two
  places rather than none. Same discipline as 0.7.1's Port.
  DRY RUN BY DEFAULT. /rsmbac import reports what would move and changes nothing; /rsmbac import
  confirm does it. It is not reversible by any command here, and it warns before starting when the
  structure does not have room. Op-gated, unlike info.
  REACHING A FOREIGN MOD'S CONTAINER. Both AutocrafterBlockEntity and Cable Tiers'
  TieredAutocrafterBlockEntity hold a PRIVATE PatternInventory named patternContainer -- the latter
  copied the former -- and neither exposes it. The field is found BY TYPE, not by name, so it works
  for RS, Cable Tiers and any addon built on the same class with no compile-time dependency on any
  of them. Our own Pattern Storage is skipped by type; it holds one too.
  AND THE PART THAT COULD NOT BE REASONED ABOUT. Under NeoForge every mod is a named MODULE, where
  setAccessible on another module's private field is exactly the sort of thing that compiles and
  then throws. A gametest seeds a real RS Autocrafter and imports from it, so the module question is
  answered by executing it. RS's Autocrafter stands in for Cable Tiers': same class, and only one is
  present in a dev run. 22 gametests.


0.7.1
-----
  THE PORT VERIFIES ITS WRITE. Asked directly before trusting a Port with a base's worth of
  patterns: can piping them in delete any? The audit says the main deletion mode is already
  impossible -- firstFreeSlot does not trust its hint, it scans forward confirming getItem().isEmpty()
  and returns only a slot it has just proven empty, so the Port cannot overwrite a pattern.
  ONE SMELL FOUND AND CLOSED. StructurePatterns.setItem silently does nothing if it cannot resolve
  the slot to a block, and insertItem had already committed to returning count-1 -- telling the pipe
  "I took one". Every path reaching it today passes a slot the same view just produced, so it is in
  range by construction, but that is a proof about the current call graph and the failure it guards
  is a silent deletion. The Port now reads the slot back and REFUSES if the write did not land, so
  the stack stays in the pipe where it can be seen, with an error naming the position.
  A new gametest fills a whole storage block one insert at a time, then counts: 54 in, 54 present,
  and the 55th refused rather than swallowed. Verified by breaking it -- with every insert pointed
  at slot 0 it reports "the port accepted a pattern into a full structure -- it was destroyed".
  21 gametests.


0.7.0
-----
  THE PATTERN PUSH BUDGET, SET FROM A MEASUREMENT. 0.6.0 took LavaSurf's seven-hour load to about
  six minutes. Six minutes was still the bound doing it, not the work: 2,800 patterns is about
  0.6ms of actual work, and he was waiting six minutes for it.
  TWO THINGS WERE WRONG. The budget was EIGHT PER REFRESH and a refresh happens once a second, so
  the real rate was eight patterns a second while 19 of every 20 ticks did nothing about a backlog
  the crafter knew it had. And the drain lived inside refreshStateOccasionally, so it inherited a
  cadence meant for the shape scan -- two different jobs with opposite right answers, since a scan
  walks 4,096 positions and needs to be rare, and a push is sub-microsecond and needs to be prompt.
  MEASURED, NOT GUESSED. tools: ./gradlew pushCheck, a new headless harness. It works because RS's
  whole push path -- PatternProviderNetworkNode, ParentContainer.add, PatternRepositoryImpl -- is in
  the api module with NO net.minecraft references at all, so the real classes run in a plain JVM.
  A push costs about 0.2us. The repository is O(1) per pattern, not O(patterns). Going from zero to
  SIXTEEN listeners moves the cost by about three NANOSECONDS each -- so the listener storm the old
  constant was chosen to avoid is not, for the notification mechanism itself, where the money is.
  Eight a second was slow by roughly four orders of magnitude.
  AND ONE DESIGN THE MEASUREMENT KILLED. setPattern is a bare array store before the node joins a
  network, and onAddedIntoContainer walks the array itself -- so filling first and joining once
  looked strictly better. Measured, it is a wash at LavaSurf's size and WORSE at maximum (4.38ms vs
  6.14ms), because joining makes RS walk all 148,176 slots to find 20,000 patterns. Not built.
  A TIME BUDGET RATHER THAN A COUNT, because the cost of a push is not constant: it grows mildly
  with the patterns already registered (0.14us at 1,000, 0.43us at 100,000) and with how many
  screens are watching. A count tuned for one is wrong for the other. A time budget also absorbs
  the one thing headless cannot price -- what a real grid listener does inside onAdded -- by
  fitting fewer pushes into the same slice. maxPatternPushMicrosPerTick, default 2000 (2ms), which
  is about nine thousand pushes a tick. The clock is read every 64 slots, because nanoTime costs
  about a tenth of the push it measures.
  The view the drain reads is cached from the last refresh, since building it means a shape find.
  Its staleness is exactly the refresh's staleness, and it is dropped the moment the structure stops
  being formed.
  Verified by breaking it: with the old eight-per-refresh bound restored, the new gametest reports
  "patterns are still waiting to reach the network after 50 ticks". 36 shape cases, 25 refresh
  scenarios, 79 asset checks, 56 recipe scenarios, 14 budget checks, 20 gametests.


0.6.0
-----
  THE SEVEN-HOUR LOAD. Reported from a survival world: after a restart, patterns took about seven
  hours to all become craftable, arriving in slot order -- "only the first 101 slots showup". Two
  causes, both of which made load time scale with the SIZE OF THE BOX instead of the number of
  recipes in it.
  FIRST, empty slots spent the budget. markAllDirty marked every slot whether or not it held
  anything, and the Controller's budget of eight pushes per refresh is spent on an empty slot
  exactly as on a real pattern -- to push a null into a node slot that was already null. A 16^3
  holding a hundred patterns paid for 148,176 pushes to deliver a hundred. It now marks only
  occupied slots, which is sound because the method means "the node was just rebuilt and holds
  nothing": pushing null into an already-null slot cannot change what the network believes.
  Removals are untouched -- they go through the inventory listener, one slot at a time.
  SECOND, PatternChanges is a LATCH, NOT A LEVEL. RefreshSchedule clears it on every scan, so the
  single bump a world load produces bought exactly ONE one-second refresh; the backlog behind it
  then drained at the ten-second safety scan. Eight patterns per ten seconds, which is where the
  seven hours came from. The pusher now re-bumps while dirty slots remain, which is the "there is
  still work" level the schedule cannot see.
  Together, for the reported structure: about seven hours to about six minutes.
  AND THE FOUR-FPS PATTERN SCREEN. Both render loops walked every slot in the structure once per
  frame, and canDisplayOutput -- which RS calls while drawing each of the ~90 visible slots -- walked
  it AGAIN, as PatternMenu.containsPattern. At the reported 21,600 slots that is over two million
  container reads a frame. layout() now remembers the slots it placed, rendering iterates those, and
  canDisplayOutput answers from an identity set of the stacks placed this frame. containsPattern is
  deleted rather than left to be called again by accident.
  A STRUCTURE TOO BIG FOR ONE WINDOW NOW SAYS SO. A container slot index is a short on the wire in
  both directions, so a menu above 32,767 slots hands out indices that arrive negative and a click
  lands on the wrong pattern -- and the content packet for that many patterns exceeds Minecraft's
  8 MiB ceiling, which disconnects the player and reads as the world corrupting. This is MINECRAFT'S
  limit and not Refined Storage's: RS's PatternProviderNetworkNode is a plain Pattern[] with no
  bound. So it is applied to the SCREEN, never to capacity -- the crafter still crafts at any size,
  and clamping capacity would in fact break pushing outright, since pushPatternsIfChanged refuses to
  write while the view and the node disagree on size. Temporary; the windowed menu removes it.
  Verified by breaking it: with the old markAllDirty restored, the new gametest reports "re-pushing 2
  patterns held in 108 slots cost 108 pushes". 36 shape cases, 25 refresh scenarios, 79 asset checks,
  56 recipe scenarios, 14 budget checks, 19 gametests.


0.5.0
-----
  THE PATTERN PORT. A wall block that patterns can be piped into, any number per structure. It had to
  be a block: Pattern Storage is interior, so all six of its faces touch other structure blocks and no
  pipe can ever reach one. The Controller could have carried the handler instead and needed no new
  block, but its face is a screen showing what the crafter is doing, and a pipe on it hides that.
  TWO VIRTUAL SLOTS, from Reborn Storage's TileIoPort. Slot 0 inserts and always reads empty; slot 1
  extracts and shows only the last pattern in. Better than one slot per pattern in two ways: an RS
  External Storage pointed at it cannot see or drain the crafter's patterns, and nothing walks 148,000
  slots looking for a free one -- each storage block answers from a bound it already keeps.
  AN UNFORMED STRUCTURE REFUSES rather than swallowing, which is verified by breaking it: with the
  insert changed to swallow, two gametests fail.
  AND THE LATENCY IT EXPOSED. Patterns had taken up to ten seconds to reach the network since 0.1.9,
  because the Controller's refresh is driven by StructureChanges and a pattern arriving is not a block
  change -- so only the ten-second safety scan ever pushed one. Eight patterns per ten seconds means a
  54-slot storage block took over a minute to become craftable. PatternChanges is the counter that
  fixes it, rate-limited rather than debounced: a debounce is right for a construction stick and
  exactly wrong for a pipe, which never stops and would restart the window forever.
  Textures: port.png is generated from our own Casing, alongside the Controller faces, by
  tools/GenerateTextures.java (renamed from GenerateControllerTextures now it has two customers).
  36 shape cases, 22 refresh scenarios, 79 asset checks, 56 recipe scenarios, 18 gametests.


0.4.0
-----
  THE CRAFTING TICK BUDGET. A maxed structure asks RS for 175,552 steps per tick and RS performs
  them synchronously before the tick can end -- so a 150ms crafting tick IS a 150ms tick, the server
  runs at ~6 TPS, and every mob, machine and chunk gets those same 6 ticks. Reported as "my world
  TPS is always under 10 while the crafter runs; is there no way around that?"
  There is, and it costs almost nothing. Ticks already run back to back and the crafter fills them,
  so it gets ~100% of wall-clock time today. Under a 45ms budget it gets 45/50ths instead: about a
  tenth less crafting per second for FOUR TIMES the tick rate. A 100k craft goes from ~34s to ~37s
  and the world runs normally while it happens.
  WHY THE COMPARISON TO AE2 WAS RIGHT. ExtendedAE's Assembler Matrix gives each crafter block a
  fixed set of threads on a cooldown (TileAssemblerMatrixCrafter: CraftingThread[] threads,
  MAX_THREAD, COOL_TIME) -- its per-tick cost is proportional to the number of threads and never to
  the number of crafts completed, so a big job takes MORE TICKS, never a longer one. Base AE2 does
  the same, bounding itself by getCoProcessors(). RS's engine is iterative
  (for i in 0..steps: pattern.step) so we cannot adopt that shape without replacing the engine; a
  budget applies the same idea to the engine we have.
  CONTROL LAW, ASYMMETRIC ON PURPOSE: back off immediately and proportionally, recover an eighth at
  a time. A long tick is the thing being prevented, so one overshoot corrects on the next tick
  rather than decaying while the world stutters; recovery is gentle because a structure hovering at
  the limit would otherwise visibly pulse. Proportional control needs no model of what a step costs,
  which is just as well -- a step that finds nothing costs almost nothing and one that substitutes a
  worn tool costs a great deal.
  NOTHING HAPPENS WHEN NOTHING IS WRONG. While ticks fit, the allowance climbs back to the full rate
  and stays, so a small structure, an idle one, or a big one on a server with headroom is completely
  unaffected. Only a structure currently overrunning is throttled, and only while it does.
  maxCraftingMillisPerTick, default 45, 0 restores the old behaviour exactly. First config this mod
  has had. /rsmbac info gains a budget line, because a throttled structure and a slow one look
  identical from in front of it.
  14 headless checks (budgetCheck), BREAK-TESTED: deleting the recovery fails exactly the three
  assertions about recovering, which is the silent failure -- a crafter that backed off and never
  came back, on a server that looks healthy.


0.3.0
-----
  FLUID SUBSTITUTION PATTERNS WORK IN THE MULTIBLOCK NOW. Reported in game as "I can't craft 1000
  cakes using RFS", and the planner said exactly why: "required with no pattern and none in
  storage: [minecraft:milk_bucket]". The pattern was reaching the node UNRESOLVED.
  THE CAUSE IS WHERE RFS PUTS ITS HOOK. Refined Fluid Substitution resolves patterns in a mixin on
  Refined Storage's own AutocrafterBlockEntity -- rfs$updateFluidSubstitutionPatterns reads that
  block entity's pattern container and pushes resolved patterns into its node. Our Controller is not
  an AutocrafterBlockEntity; it holds patterns in Pattern Storage blocks and pushes them itself, so
  that mixin never runs for us. The two hooks RFS does put on shared classes only manage pattern
  capacity. Nothing was broken on either side -- the integration simply did not exist.
  FIXED BY CALLING RFS'S OWN RESOLVER, no mixin needed: FluidSubstitutionPatternResolver.resolve is
  public static. The layout is read from the 2.0.0 bytecode rather than invented -- main pattern at
  its container slot, helpers packed sequentially from containerSize, the tail nulled, capacity
  grown to containerSize * 10 (upstream's MAX_HELPERS_PER_PATTERN is 9). Matching it means a pattern
  behaves the same in the multiblock as in an Autocrafter.
  OPTIONAL, AND PROVEN OPTIONAL. Every RFS type is named in one class, reached only through a
  ModList.isLoaded gate in another, because the JVM resolves a class when a method referencing it
  first runs -- one combined class would fail on its own availability check. All 13 gametests pass
  with RFS absent, which is the property that matters for everyone not running it.
  UNVERIFIED: the with-RFS path. No automated test can cover it -- the gametest runtime has no RFS
  on its classpath -- so this needs confirming in game.

0.2.4
-----
  THE 0.2.3 GRACE PERIOD GETS A TEST SUITE, aimed at the bug it could introduce rather than the one
  it fixed. Suppressing ACTIVE -> INACTIVE risks a screen that will NEVER go dark, which is worse
  than the flicker it replaces, and nothing pinned the expiry. Decision extracted to JoinGrace
  (pure arithmetic, time passed in, same shape as RefreshSchedule) and 12 scenarios added as
  joinGraceCheck, wired into check.
  Four of them are the expiry: suppressed one tick before the deadline, NOT suppressed at it, never
  again after it, and an unplug an hour into a session is not a join. Two more pin that the clock
  starts at the FIRST CALL rather than at tick zero -- a real save loads at an arbitrary game time
  (3,069,920 in the report), so a window measured against the level clock would pass every test
  starting at zero and never once fire in game.
  BREAK-TESTED, not just run green: with the expiry deleted, exactly those four fail and the other
  eight still pass. A suite that has never been shown to fail has not been shown to test anything.
  No behaviour change from 0.2.3.

0.2.3
-----
  THE STUCK SCREEN, FOUND AND FIXED. 0.2.2's logging caught it on its first run:
    active -> inactive (tick 3069920, node active=false, energy       -1/176795 FE)
    inactive -> active (tick 3069926, node active=true,  energy MAX_VALUE/176795 FE)
  -1 is "no network to ask". On world load the block entity ticks before joinNetworkIfNeeded has a
  network to join, so hasEnergy() is false for a few ticks and the screen is driven to INACTIVE and
  straight back. Six ticks on the server -- and PERMANENT on any client whose chunk snapshot lands
  inside that window, because the server returns to ACTIVE and then sees no further change to
  broadcast. Looks unpowered, crafts normally, cleared by relogging: the exact report, twice.
  FIX: a join grace period. ACTIVE -> INACTIVE is suppressed only while there is genuinely no
  network and only within 40 ticks of the block entity's first screen update. Bounded deliberately
  in both directions -- a screen that will not go dark is the worse bug, so a structure whose cable
  was pulled while its chunk was unloaded still reports honestly two seconds after load.
  The 0.2.2 logging stays in. It cost one run to find a bug that had survived two reports and a
  passing gametest, and it is what will settle the next one.

0.2.2
-----
  INSTRUMENTS THE STUCK SCREEN, rather than guessing at it a third time. Reported again: the
  Controller looks unpowered while the structure keeps crafting normally. That pair cannot happen
  legitimately -- RS's PatternProviderNetworkNode.doWork returns immediately unless isActive(), so
  crafting PROVES the node is active, and syncNode sets that flag and updateScreen sets the block
  state from the same hasEnergy() a few statements apart. Assets were checked and are complete
  (all 12 variants, three models, three textures), so the model path is not it.
  updateScreen now logs every transition with the old and new value, the position, the game tick,
  the node's active flag and the energy numbers. /rsmbac info gains "node (server)" and
  "energy (server)" lines beside the existing "screen (server)" one, and flags it red when the node
  and the screen disagree.
  WHY NOT A FIX: this was reported once before and closed in 0.0.8 on a gametest that passed --
  but a gametest has no client, so it only ever exercised the half that was already correct, and
  the report came back. Buying the observation first.
  Also: hasEnergy and the diagnostics now read the network's energy through one method, so the
  report cannot drift from the decision it is reporting on.

  encoded. Searching for the thing you wanted to craft found nothing; searching "pattern" found

  the structure's speed is the SUM of its CPU tiers (1x + 4x + 16x = 21, chosen because it is

0.1.12
------
  FIX: an unformed Crafter Controller could not be broken, and nothing could be placed next to it.
  Reported in game as Refined Storage's own toast, "You are not allowed to break the Crafter
  Controller". Nothing in rsmc was denying it: RS runs a global BlockEvent.BreakEvent handler over
  any position exposing a network-node capability, and SecurityHelper.isAllowed reads
  "network == null ? false : ..." -- NO NETWORK MEANS DENIED, with no owner and nothing to
  protect. The Controller only joined a network from ensureCapacity, which syncNode reached only
  after its "not formed" early exit, so an unformed one never joined. canPlaceNetworkNode checks
  all six neighbours the same way, so the structure could be neither finished nor removed. It now
  joins while unformed, at zero capacity and IDLE, exactly as ShellBlockEntity has always done --
  the Frame and Casing were never affected for that reason. Only on the unformed path: joining
  early on a formed structure forced an immediate resize rebuild that delayed activation by a
  tick, which apoweredstructuregoesactive caught. New gametest (11 total), confirmed to fail with
  the fix removed.
0.1.11
------
  Four changes from playing with 0.1.10. (1) Crafter Casing was one ingredient away from Crafter
  Frame in the recipe book; it now takes basic processors in the top and bottom centre, so the two
  are distinct shapes. (2) CPU tiers renamed 1K/4K/16K/64K -> 1x/4x/16x/64x. K reads as CAPACITY,
  which is what it means on every other block wearing it, and these store nothing -- a 64x CPU is
  64 steps per tick, not 64,000 of anything. Rung ratio and recipe ladder unchanged, only the
  label. (3) CPU recipes put the quartz enriched iron at the bottom and swap the redstone for a
  vanilla crafter, matching the 1x recipe. (4) A registry alias for the rename was written, tested
  and then REMOVED on Wraith's call -- no playthrough to protect, so it was machinery guarding a
  failure nobody will hit. Existing worlds will lose their CPU blocks; that is accepted. Noted in
  CHANGELOG for when it matters: MissingMappingsEvent does NOT exist in NeoForge 1.21,
  DeferredRegister.addAlias is the replacement, and it needs applying to blocks AND items.
  The rename was done as cpu_1k -> cpu_1x, never bare 1k -> 1x: a blanket replace would have
  rewritten refinedstorage:1k_storage_part in the Pattern Storage recipe into a nonexistent item.
0.1.10

  #5: every block is craftable. Frame and Casing as proposed (quartz enriched iron/copper round a

0.1.9
-----
  #3's mechanism half. The Controller used to run a full MultiblockShape.find -- flood fill plus
  box walk, up to 4096 positions -- every 20 ticks forever, whether or not anything had changed;
  measured at 0.19 ms/tick for a machine doing nothing. Now change-driven: StructureChanges is a
  global counter bumped by every structure block's onPlace/onRemove (which catches pistons,
  commands and other mods, unlike a player event), and RefreshSchedule debounces 5 ticks so a
  construction stick placing a wall costs ONE scan, not hundreds. A 10-second safety scan stays,
  because the counter only sees rsmc blocks and something exotic could still break a box. Idle
  cost drops 10x and ordinary changes are noticed FASTER -- a quarter second instead of up to one.
  New refreshCheck (15), wired into build. It found a real overflow on its first run: lastScan
  seeded to Long.MIN_VALUE made "now - lastScan" negative, so a freshly loaded Controller would
  never have scanned at all.
0.1.8
-----
  Two fixes to 0.1.7, both reported after using it. (1) The outline was NOT see-through:
  RenderType.lines() is depth-tested, and a MultiBufferSource re-applies the render type's own GL
  state at endBatch, so disabling depth beforehand was overwritten. The class comment claimed
  see-through and the code did the opposite. Now the lines state is set up, depth is disabled
  AFTER that setup, and the box is drawn immediately instead of queued -- so a wrong block inside
  the crafter is actually visible. (2) The chat message ate the block placement that came with the
  right-click: the unformed path returned CONSUME. It returns PASS now, so building against the
  structure works, and the message is rate-limited to once a second per player so a wall of
  right-clicks does not become a wall of text. Right-clicking the Controller always speaks.
