RSMC - WHAT EACH VERSION DID
============================

One or two lines per version, newest first. This file is the short form; CHANGELOG.md is
the detailed history and carries the reasoning. BOTH ARE MAINTAINED - every version bump
gets an entry in each.

The rule is adopted from rstweaks, where it was learned the hard way: versions 0.2.18
through 0.2.46 of that mod were never written down and the detail is unrecoverable.

0.5.0
-----
  THE PATTERN PORT. A wall block that patterns can be piped into, any number per structure. It had to
  be a block: Pattern Storage is interior, so all six of its faces touch other structure blocks and no
  pipe can ever reach one. The Controller could have carried the handler instead and needed no new
  block, but its face is a screen showing what the crafter is doing, and a pipe on it hides that.
  TWO VIRTUAL SLOTS, from Reborn Storage's TileIoPort. Slot 0 inserts and always reads empty; slot 1
  extracts and shows only the last pattern in. Better than one slot per pattern in two ways: an RS
  External Storage pointed at it cannot see or drain the crafter's patterns, and nothing walks 148,000
  slots looking for a free one -- each storage block answers from a bound it already keeps.
  AN UNFORMED STRUCTURE REFUSES rather than swallowing, which is verified by breaking it: with the
  insert changed to swallow, two gametests fail.
  AND THE LATENCY IT EXPOSED. Patterns had taken up to ten seconds to reach the network since 0.1.9,
  because the Controller's refresh is driven by StructureChanges and a pattern arriving is not a block
  change -- so only the ten-second safety scan ever pushed one. Eight patterns per ten seconds means a
  54-slot storage block took over a minute to become craftable. PatternChanges is the counter that
  fixes it, rate-limited rather than debounced: a debounce is right for a construction stick and
  exactly wrong for a pipe, which never stops and would restart the window forever.
  Textures: port.png is generated from our own Casing, alongside the Controller faces, by
  tools/GenerateTextures.java (renamed from GenerateControllerTextures now it has two customers).
  36 shape cases, 22 refresh scenarios, 79 asset checks, 56 recipe scenarios, 18 gametests.


0.4.0
-----
  THE CRAFTING TICK BUDGET. A maxed structure asks RS for 175,552 steps per tick and RS performs
  them synchronously before the tick can end -- so a 150ms crafting tick IS a 150ms tick, the server
  runs at ~6 TPS, and every mob, machine and chunk gets those same 6 ticks. Reported as "my world
  TPS is always under 10 while the crafter runs; is there no way around that?"
  There is, and it costs almost nothing. Ticks already run back to back and the crafter fills them,
  so it gets ~100% of wall-clock time today. Under a 45ms budget it gets 45/50ths instead: about a
  tenth less crafting per second for FOUR TIMES the tick rate. A 100k craft goes from ~34s to ~37s
  and the world runs normally while it happens.
  WHY THE COMPARISON TO AE2 WAS RIGHT. ExtendedAE's Assembler Matrix gives each crafter block a
  fixed set of threads on a cooldown (TileAssemblerMatrixCrafter: CraftingThread[] threads,
  MAX_THREAD, COOL_TIME) -- its per-tick cost is proportional to the number of threads and never to
  the number of crafts completed, so a big job takes MORE TICKS, never a longer one. Base AE2 does
  the same, bounding itself by getCoProcessors(). RS's engine is iterative
  (for i in 0..steps: pattern.step) so we cannot adopt that shape without replacing the engine; a
  budget applies the same idea to the engine we have.
  CONTROL LAW, ASYMMETRIC ON PURPOSE: back off immediately and proportionally, recover an eighth at
  a time. A long tick is the thing being prevented, so one overshoot corrects on the next tick
  rather than decaying while the world stutters; recovery is gentle because a structure hovering at
  the limit would otherwise visibly pulse. Proportional control needs no model of what a step costs,
  which is just as well -- a step that finds nothing costs almost nothing and one that substitutes a
  worn tool costs a great deal.
  NOTHING HAPPENS WHEN NOTHING IS WRONG. While ticks fit, the allowance climbs back to the full rate
  and stays, so a small structure, an idle one, or a big one on a server with headroom is completely
  unaffected. Only a structure currently overrunning is throttled, and only while it does.
  maxCraftingMillisPerTick, default 45, 0 restores the old behaviour exactly. First config this mod
  has had. /rsmbac info gains a budget line, because a throttled structure and a slow one look
  identical from in front of it.
  14 headless checks (budgetCheck), BREAK-TESTED: deleting the recovery fails exactly the three
  assertions about recovering, which is the silent failure -- a crafter that backed off and never
  came back, on a server that looks healthy.


0.3.0
-----
  FLUID SUBSTITUTION PATTERNS WORK IN THE MULTIBLOCK NOW. Reported in game as "I can't craft 1000
  cakes using RFS", and the planner said exactly why: "required with no pattern and none in
  storage: [minecraft:milk_bucket]". The pattern was reaching the node UNRESOLVED.
  THE CAUSE IS WHERE RFS PUTS ITS HOOK. Refined Fluid Substitution resolves patterns in a mixin on
  Refined Storage's own AutocrafterBlockEntity -- rfs$updateFluidSubstitutionPatterns reads that
  block entity's pattern container and pushes resolved patterns into its node. Our Controller is not
  an AutocrafterBlockEntity; it holds patterns in Pattern Storage blocks and pushes them itself, so
  that mixin never runs for us. The two hooks RFS does put on shared classes only manage pattern
  capacity. Nothing was broken on either side -- the integration simply did not exist.
  FIXED BY CALLING RFS'S OWN RESOLVER, no mixin needed: FluidSubstitutionPatternResolver.resolve is
  public static. The layout is read from the 2.0.0 bytecode rather than invented -- main pattern at
  its container slot, helpers packed sequentially from containerSize, the tail nulled, capacity
  grown to containerSize * 10 (upstream's MAX_HELPERS_PER_PATTERN is 9). Matching it means a pattern
  behaves the same in the multiblock as in an Autocrafter.
  OPTIONAL, AND PROVEN OPTIONAL. Every RFS type is named in one class, reached only through a
  ModList.isLoaded gate in another, because the JVM resolves a class when a method referencing it
  first runs -- one combined class would fail on its own availability check. All 13 gametests pass
  with RFS absent, which is the property that matters for everyone not running it.
  UNVERIFIED: the with-RFS path. No automated test can cover it -- the gametest runtime has no RFS
  on its classpath -- so this needs confirming in game.

0.2.4
-----
  THE 0.2.3 GRACE PERIOD GETS A TEST SUITE, aimed at the bug it could introduce rather than the one
  it fixed. Suppressing ACTIVE -> INACTIVE risks a screen that will NEVER go dark, which is worse
  than the flicker it replaces, and nothing pinned the expiry. Decision extracted to JoinGrace
  (pure arithmetic, time passed in, same shape as RefreshSchedule) and 12 scenarios added as
  joinGraceCheck, wired into check.
  Four of them are the expiry: suppressed one tick before the deadline, NOT suppressed at it, never
  again after it, and an unplug an hour into a session is not a join. Two more pin that the clock
  starts at the FIRST CALL rather than at tick zero -- a real save loads at an arbitrary game time
  (3,069,920 in the report), so a window measured against the level clock would pass every test
  starting at zero and never once fire in game.
  BREAK-TESTED, not just run green: with the expiry deleted, exactly those four fail and the other
  eight still pass. A suite that has never been shown to fail has not been shown to test anything.
  No behaviour change from 0.2.3.

0.2.3
-----
  THE STUCK SCREEN, FOUND AND FIXED. 0.2.2's logging caught it on its first run:
    active -> inactive (tick 3069920, node active=false, energy       -1/176795 FE)
    inactive -> active (tick 3069926, node active=true,  energy MAX_VALUE/176795 FE)
  -1 is "no network to ask". On world load the block entity ticks before joinNetworkIfNeeded has a
  network to join, so hasEnergy() is false for a few ticks and the screen is driven to INACTIVE and
  straight back. Six ticks on the server -- and PERMANENT on any client whose chunk snapshot lands
  inside that window, because the server returns to ACTIVE and then sees no further change to
  broadcast. Looks unpowered, crafts normally, cleared by relogging: the exact report, twice.
  FIX: a join grace period. ACTIVE -> INACTIVE is suppressed only while there is genuinely no
  network and only within 40 ticks of the block entity's first screen update. Bounded deliberately
  in both directions -- a screen that will not go dark is the worse bug, so a structure whose cable
  was pulled while its chunk was unloaded still reports honestly two seconds after load.
  The 0.2.2 logging stays in. It cost one run to find a bug that had survived two reports and a
  passing gametest, and it is what will settle the next one.

0.2.2
-----
  INSTRUMENTS THE STUCK SCREEN, rather than guessing at it a third time. Reported again: the
  Controller looks unpowered while the structure keeps crafting normally. That pair cannot happen
  legitimately -- RS's PatternProviderNetworkNode.doWork returns immediately unless isActive(), so
  crafting PROVES the node is active, and syncNode sets that flag and updateScreen sets the block
  state from the same hasEnergy() a few statements apart. Assets were checked and are complete
  (all 12 variants, three models, three textures), so the model path is not it.
  updateScreen now logs every transition with the old and new value, the position, the game tick,
  the node's active flag and the energy numbers. /rsmbac info gains "node (server)" and
  "energy (server)" lines beside the existing "screen (server)" one, and flags it red when the node
  and the screen disagree.
  WHY NOT A FIX: this was reported once before and closed in 0.0.8 on a gametest that passed --
  but a gametest has no client, so it only ever exercised the half that was already correct, and
  the report came back. Buying the observation first.
  Also: hasEnergy and the diagnostics now read the network's energy through one method, so the
  report cannot drift from the decision it is reporting on.

0.1.12
------
  FIX: an unformed Crafter Controller could not be broken, and nothing could be placed next to it.
  Reported in game as Refined Storage's own toast, "You are not allowed to break the Crafter
  Controller". Nothing in rsmc was denying it: RS runs a global BlockEvent.BreakEvent handler over
  any position exposing a network-node capability, and SecurityHelper.isAllowed reads
  "network == null ? false : ..." -- NO NETWORK MEANS DENIED, with no owner and nothing to
  protect. The Controller only joined a network from ensureCapacity, which syncNode reached only
  after its "not formed" early exit, so an unformed one never joined. canPlaceNetworkNode checks
  all six neighbours the same way, so the structure could be neither finished nor removed. It now
  joins while unformed, at zero capacity and IDLE, exactly as ShellBlockEntity has always done --
  the Frame and Casing were never affected for that reason. Only on the unformed path: joining
  early on a formed structure forced an immediate resize rebuild that delayed activation by a
  tick, which apoweredstructuregoesactive caught. New gametest (11 total), confirmed to fail with
  the fix removed.
0.1.11
------
  Four changes from playing with 0.1.10. (1) Crafter Casing was one ingredient away from Crafter
  Frame in the recipe book; it now takes basic processors in the top and bottom centre, so the two
  are distinct shapes. (2) CPU tiers renamed 1K/4K/16K/64K -> 1x/4x/16x/64x. K reads as CAPACITY,
  which is what it means on every other block wearing it, and these store nothing -- a 64x CPU is
  64 steps per tick, not 64,000 of anything. Rung ratio and recipe ladder unchanged, only the
  label. (3) CPU recipes put the quartz enriched iron at the bottom and swap the redstone for a
  vanilla crafter, matching the 1x recipe. (4) A registry alias for the rename was written, tested
  and then REMOVED on Wraith's call -- no playthrough to protect, so it was machinery guarding a
  failure nobody will hit. Existing worlds will lose their CPU blocks; that is accepted. Noted in
  CHANGELOG for when it matters: MissingMappingsEvent does NOT exist in NeoForge 1.21,
  DeferredRegister.addAlias is the replacement, and it needs applying to blocks AND items.
  The rename was done as cpu_1k -> cpu_1x, never bare 1k -> 1x: a blanket replace would have
  rewritten refinedstorage:1k_storage_part in the Pattern Storage recipe into a nonexistent item.
0.1.10
------
  #5: every block is craftable. Frame and Casing as proposed (quartz enriched iron/copper round a
  machine casing, yield 1 -- the entry cost Wraith confirmed is deliberate). 1K CPU is Reborn's
  recipe with crafting_table swapped for minecraft:crafter; Pattern Storage is Reborn's as-is.
  The CPU ladder mirrors RS's storage parts EXACTLY -- same PEP/SRS/PSP shape, 3 of the tier below
  plus 4 processors of the matching grade -- chosen over 4x so tiering up is a genuine reward and

  the proposal and needed inventing: a Casing with refinedstorage:network_card in its face, which
  is literally the item that carries a network connection in RS. New recipeCheck (48), wired into
  build: it verifies every ingredient id against the REAL Refined Storage jar, because a typo'd
  item does not crash -- the recipe is silently dropped at datapack load and the block just cannot
  be made. Confirmed by typoing network_card. Skips the RS half gracefully on a fresh clone, where
  libs/ is empty.
0.1.9
-----
  #3's mechanism half. The Controller used to run a full MultiblockShape.find -- flood fill plus
  box walk, up to 4096 positions -- every 20 ticks forever, whether or not anything had changed;
  measured at 0.19 ms/tick for a machine doing nothing. Now change-driven: StructureChanges is a
  global counter bumped by every structure block's onPlace/onRemove (which catches pistons,
  commands and other mods, unlike a player event), and RefreshSchedule debounces 5 ticks so a
  construction stick placing a wall costs ONE scan, not hundreds. A 10-second safety scan stays,
  because the counter only sees rsmc blocks and something exotic could still break a box. Idle
  cost drops 10x and ordinary changes are noticed FASTER -- a quarter second instead of up to one.
  New refreshCheck (15), wired into build. It found a real overflow on its first run: lastScan
  seeded to Long.MIN_VALUE made "now - lastScan" negative, so a freshly loaded Controller would
  never have scanned at all.
0.1.8
-----
  Two fixes to 0.1.7, both reported after using it. (1) The outline was NOT see-through:
  RenderType.lines() is depth-tested, and a MultiBufferSource re-applies the render type's own GL
  state at endBatch, so disabling depth beforehand was overwritten. The class comment claimed
  see-through and the code did the opposite. Now the lines state is set up, depth is disabled
  AFTER that setup, and the box is drawn immediately instead of queued -- so a wrong block inside
  the crafter is actually visible. (2) The chat message ate the block placement that came with the
  right-click: the unformed path returned CONSUME. It returns PASS now, so building against the
  structure works, and the message is rate-limited to once a second per player so a wall of
  right-clicks does not become a wall of text. Right-clicking the Controller always speaks.

  the offending block for 15 seconds, drawn without depth testing so it is visible through the

  Every other block still explains in chat, and now names what the position actually needed
